# Palantir Ontology Language：理念、方法论与执行方式

> 本文是对 Palantir 官方 Ontology 页面及 Foundry 文档的中文整理，不是逐句翻译。重点放在其如何把数据转化为业务决策和行动。

## 一句话理解

Palantir 的 Ontology 不只是给数据加标签，而是把企业中的数据、业务对象、关系、逻辑、动作、权限和决策流程，统一建模成一个可以被人和 AI 共同理解、查询、分析并执行的业务层。

官方将 Ontology 拆成三部分：

1. **Language**：描述业务世界的对象、关系和动作；
2. **Engine**：提供可扩展的读写架构；
3. **Toolchain**：让开发者基于 Ontology 构建应用和 AI 工作流。

- [Palantir Foundry Platform Summary](https://www.palantir.com/docs/foundry/getting-started/foundry-platform-summary-llm)

## 一、核心理念：从数据中心转向决策中心

传统企业系统往往是：

```text
数据源 → 数据仓库 → 报表 → 人工判断 → 外部系统执行
```

Ontology 试图把它变成：

```text
现实世界对象 → 数据与关系 → 判断逻辑 → 可执行动作 → 结果回写
```

它关心的不只是“这个字段是什么意思”，还关心：

- 当前对象处于什么状态；
- 它与哪些对象有关；
- 谁能查看或修改；
- 哪些动作可以执行；
- 动作执行后会改变什么；
- 变化是否可以审计和回溯。

Palantir 官方称，Ontology 在很多场景中充当组织的数字孪生，同时包含语义元素和动力元素。

- [Ontology Overview](https://palantir.com/docs/foundry/ontology/overview/)

## 二、Ontology Language 的基本语法

### 1. Object：对象

对象代表现实中的实体，例如客户、订单、飞机、工厂、设备、维修任务和员工。对象不是单纯复制数据库表，而是要定义它在业务中的含义、状态、关系、权限和可执行操作。

### 2. Property：属性

属性描述对象的状态，例如订单金额、客户等级、设备位置、库存数量和维修优先级。属性还可以附带来源、类型、展示方式、计算逻辑、权限和编辑规则。

### 3. Link：关系

Link 描述对象之间的业务关系：

```text
客户 → 拥有 → 订单
订单 → 包含 → 产品
航班 → 使用 → 飞机
设备 → 需要 → 维修任务
```

Palantir 将关系本身视为可复用业务资产，而不是查询时临时拼接的 Join。官方文档把 Link Type 定义为两个对象类型之间的关系结构，把具体 Link 定义为两个具体对象之间的一次现实关系。

- [Link Types Overview](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview)

### 4. Action：动作

Action 描述组织可以对对象做什么，例如审批订单、分配工程师、调整库存、取消航班和创建补货任务。

这一步把系统从“只能读”推进到“可以受控地改变业务状态”。复杂动作可以由 Functions 承载；Functions 能查询对象、遍历关系、聚合数据、修改对象和调用外部 API。

- [Functions Overview](https://www.palantir.com/docs/foundry/functions/overview)

## 三、方法论：先建模业务，再组织数据和应用

### 第一步：识别关键对象

先问“业务中真正重要的东西是什么”，而不是先问“我们有哪些表”。供应链可能包括供应商、工厂、原材料、采购订单、运输任务、仓库和客户订单。

### 第二步：建立关系网络

把“谁提供什么、谁依赖什么、什么影响什么”表达出来。关系越明确，查询、分析、权限和动作越容易复用。

### 第三步：把数据映射到对象

ERP、CRM、Excel、传感器、API、日志和文档先进入数据层，再映射为对象、属性和关系。官方文档强调，Ontology 是把数据集和模型连接到现实业务对象，而不只是做数据目录。

- [Introductory Concepts](https://www.palantir.com/docs/foundry/getting-started/introductory-concepts)

### 第四步：定义状态变化和业务逻辑

例如：

```text
如果库存低于安全线：
    创建补货任务
    通知采购负责人
    更新订单风险状态
```

### 第五步：接入应用和 AI

最终目标不是建一个漂亮模型，而是让对象进入操作台、分析工具、审批流程、AI 助手和 Agent。

## 四、执行架构

```text
数据层：数据源、表格、文档、事件、日志
语义层：对象、属性、关系、状态
智能层：模型、检索、规则、函数、Agent
动作层：API、审批、写回、人工接管、回滚
治理层：身份、权限、审计、评估、监控、成本
```

AI 不只是从文本中猜答案，而是可以在权限范围内访问真实对象、关系和业务函数，再提出建议或触发受控动作。Palantir AIP 官方将其定位为构建在 Ontology 和开发者工具链之上的 AI 工作流、Agent 和函数平台。

- [AIP Overview](https://www.palantir.com/docs/foundry/aip)

## 五、与普通语义层的区别

普通语义层主要回答：

> 这个字段是什么意思？

Ontology 还要回答：

> 现在发生了什么？谁能改变它？应该做什么？改变之后会发生什么？

所以它同时描述“意义”和“行动”。权限也不是外围配置，而是动作的一部分：执行 Action 需要对动作类型和被修改的 Ontology 资源拥有相应权限。

- [Ontology Permissions](https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions)

## 六、示例：设备故障处理

传统方式：

```text
传感器报警 → 工程师打开多个系统 → 人工查记录和备件 → 电话确认 → 手动建维修单
```

Ontology 方式：

```text
报警事件
  ↓
关联设备、历史故障、备件和工程师
  ↓
判断优先级与影响范围
  ↓
推荐处理方案
  ↓
创建维修任务
  ↓
更新设备状态并记录过程
```

AI 可以识别异常、查询上下文、总结故障并推荐方案；是否真的创建任务或修改状态，则由权限、动作定义、审批和审计机制控制。

## 七、可迁移的方法论

1. 从“表”转向“对象”：数据对应现实中的什么东西？
2. 从“字段”转向“状态”：对象现在处于什么阶段？
3. 从“报表”转向“动作”：看到结果之后谁应该做什么？
4. 从“应用孤岛”转向“共享业务模型”：不同应用是否使用同一套对象和关系？
5. 从“AI 生成答案”转向“AI 参与流程”：AI 是否能在边界内查询、判断、调用工具和留下记录？

## 结论

Palantir Ontology Language 的核心，不是增加一个更复杂的数据模型，而是把企业业务表达成一套共同语言：

```text
对象：业务里有什么
关系：它们如何关联
状态：现在发生了什么
逻辑：应该如何判断
动作：可以做什么
权限：谁有资格做
反馈：做完之后发生了什么
```

最终目标是让组织看懂自己的现实，并把判断转化为受控行动。
