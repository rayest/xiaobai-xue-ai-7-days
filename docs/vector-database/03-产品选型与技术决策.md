# 向量数据库产品选型与技术决策

## 1. 先定义问题，再选产品

先写清楚数据对象、查询形态和约束：向量维度与数量、写入增长、Top-K、过滤字段、是否混合检索、P95/P99 延迟、可用性、数据地域、租户隔离、预算和团队运维能力。

一个“100 万向量、低 QPS 的内部知识库”和“数十亿向量、严格 P99 的推荐系统”不是同一个选型题。

## 2. 主要方案类别

| 类别 | 适合场景 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| 专用向量数据库 | 复杂过滤、混合检索、多租户、规模化 RAG | 向量能力完整，索引和查询语义清晰 | 需要引入新组件并运维 |
| 关系数据库向量扩展 | 已有 SQL、规模中小、事务关联强 | 复用账号、事务、备份和 SQL | 超大规模/高并发时需专项压测 |
| 搜索引擎向量能力 | 关键词、全文、聚合与向量一体 | 混合搜索和运营检索成熟 | 向量索引成本、参数和版本复杂 |
| 云托管向量服务 | 希望快速上线、少运维 | 弹性、托管、服务集成方便 | 长期成本、数据驻留和供应商绑定 |
| 内存/本地 ANN 库 | 单机 PoC、边缘或离线任务 | 简单、便宜、延迟低 | 持久化、扩展、权限和治理要自行补齐 |

## 3. 决策维度

### 检索能力

确认是否支持：稠密/稀疏/多向量、metadata filter、全文、混合融合、重排前 Top-N、分组、时间过滤、删除与更新语义。不要只看“支持向量搜索”这一项。

### 性能与规模

用真实 Embedding 维度、payload 大小、查询比例和并发压测。至少测 Recall@K、P50/P95/P99 延迟、吞吐、索引构建时间、内存/磁盘占用、扩容和重启恢复时间。

### 一致性与生命周期

核对 upsert 是否幂等、写入何时可见、删除是否立即生效、快照能否跨版本恢复、索引重建是否影响查询，以及是否支持按版本双写和回滚。

### 企业治理

核对身份认证、TLS、RBAC、审计、租户隔离、备份、跨地域、监控指标、SLA、数据驻留、开源许可证和商业支持。

### 成本

总成本不只是节点价格，还包括 Embedding、重嵌入、索引内存、复制、备份、跨区流量、运维和故障成本。建立“每百万向量/月”和“每千次查询”的成本模型。

## 4. 推荐的选型流程

1. 固定一小组真实查询、相关性标注和安全约束。
2. 选择 2～4 个候选方案，统一 Embedding、切分和查询参数。
3. 做离线质量评测，再做带并发、故障和恢复的线上压测。
4. 计算 12～24 个月 TCO，记录锁定风险与迁移路径。
5. 用可回滚的灰度流量验证，再决定生产方案。

## 5. 常见误区

- 只比较 QPS，不比较 Recall@K 和尾延迟。
- 把向量维度越大等同于效果越好。
- 未建立过滤字段索引就直接上线。
- 用客户端传入的 tenant_id 作为唯一权限控制。
- 只测干净数据，不测重复、脏数据、长文档、跨语言和越权查询。
- 忽略模型升级后的向量版本、重嵌入窗口和回滚策略。
