# 向量数据库产品选型与技术决策

## 1. 先定义问题，再选产品

先写清楚数据对象、查询形态和约束：向量维度与数量、写入增长、Top-K、过滤字段、是否混合检索、P95/P99 延迟、可用性、数据地域、租户隔离、预算和团队运维能力。

一个“100 万向量、低 QPS 的内部知识库”和“数十亿向量、严格 P99 的推荐系统”不是同一个选型题。

## 2. 具体产品与方案

| 类别 | 代表产品 | 适合场景 | 主要考虑 |
| --- | --- | --- | --- |
| 专用向量数据库 | **Qdrant、Milvus、Weaviate、Chroma** | 复杂过滤、混合检索、多租户、规模化 RAG | 重点比较过滤、混合/多向量能力、集群扩展和运维成熟度 |
| 云托管向量服务 | **Pinecone、Zilliz Cloud、云厂商托管 Milvus/Qdrant** | 希望快速上线、少运维 | 重点比较区域、SLA、弹性、数据驻留、出网费用和供应商绑定 |
| 关系数据库向量扩展 | **PostgreSQL + pgvector** | 已有 SQL、规模中小、事务关联强 | 复用事务和权限体系；规模、并发、索引构建必须压测 |
| 搜索引擎向量能力 | **Elasticsearch、OpenSearch、Vespa** | 关键词、全文、聚合与向量一体 | 适合搜索平台团队；重点比较混合排序、索引成本和运维复杂度 |
| 内存/本地 ANN 库 | **FAISS、Annoy、hnswlib、LanceDB** | 单机 PoC、边缘或离线任务 | 简单便宜，但持久化、权限、复制和在线运维需自行补齐 |

### 2.1 产品如何初筛

下面是一个面向常见场景的起始 shortlist，不是脱离数据的最终结论：

| 场景 | 可以优先评估 | 选择理由 |
| --- | --- | --- |
| 想快速做 Qdrant 教程和中型 RAG | **Qdrant** | API 直观，payload filter、稀疏/稠密混合、多向量和多租户教程路径清晰 |
| 超大规模、自建集群或希望云上使用 Milvus 生态 | **Milvus / Zilliz Cloud** | 适合把分布式向量检索作为独立基础设施评估 |
| 希望托管、减少数据库运维 | **Pinecone** | 适合作为托管向量服务候选；重点核算长期成本和数据区域 |
| 已经有 PostgreSQL，数据量和并发可控 | **pgvector** | 业务表与向量可在同一数据库中管理，系统复杂度较低 |
| 既要全文检索、聚合，又要向量召回 | **Elasticsearch / OpenSearch** | 适合已有搜索引擎、日志或内容检索平台的团队 |
| 本地实验、离线批处理或嵌入式应用 | **FAISS / LanceDB / Chroma** | 上手成本低；进入多租户高可用生产前需重新评估 |

产品名称会随版本、云服务区域和商业方案变化。表中的“优先评估”只用于缩小候选范围，不能替代基准测试、合规审查和 TCO 计算。

## 3. 决策维度

### 检索能力

确认是否支持：稠密/稀疏/多向量、metadata filter、全文、混合融合、重排前 Top-N、分组、时间过滤、删除与更新语义。不要只看“支持向量搜索”这一项。

### 性能与规模

用真实 Embedding 维度、payload 大小、查询比例和并发压测。至少测 Recall@K、P50/P95/P99 延迟、吞吐、索引构建时间、内存/磁盘占用、扩容和重启恢复时间。

### 一致性与生命周期

核对 upsert 是否幂等、写入何时可见、删除是否立即生效、快照能否跨版本恢复、索引重建是否影响查询，以及是否支持按版本双写和回滚。

### 企业治理

核对身份认证、TLS、RBAC、审计、租户隔离、备份、跨地域、监控指标、SLA、数据驻留、开源许可证和商业支持。

### 成本

总成本不只是节点价格，还包括 Embedding、重嵌入、索引内存、复制、备份、跨区流量、运维和故障成本。建立“每百万向量/月”和“每千次查询”的成本模型。

## 4. 推荐的选型流程

1. 固定一小组真实查询、相关性标注和安全约束。
2. 选择 2～4 个候选方案，统一 Embedding、切分和查询参数。
3. 做离线质量评测，再做带并发、故障和恢复的线上压测。
4. 计算 12～24 个月 TCO，记录锁定风险与迁移路径。
5. 用可回滚的灰度流量验证，再决定生产方案。

## 5. 常见误区

- 只比较 QPS，不比较 Recall@K 和尾延迟。
- 把向量维度越大等同于效果越好。
- 未建立过滤字段索引就直接上线。
- 用客户端传入的 tenant_id 作为唯一权限控制。
- 只测干净数据，不测重复、脏数据、长文档、跨语言和越权查询。
- 忽略模型升级后的向量版本、重嵌入窗口和回滚策略。
