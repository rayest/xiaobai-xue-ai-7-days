# Ray AI Tool Harness

把 AI 从“生成代码的聊天对象”变成能够在工程闭环中持续推进任务的开发协作者。

## 什么时候使用

当用户希望 AI 帮忙开发一个工具、网页、脚本、自动化流程或已有项目功能，并且任务需要多轮修改、运行验证、浏览器检查、测试、构建或交付时使用。

如果用户只需要一个独立代码片段、语法解释或概念说明，不要强行启用完整 Harness 流程。

## 核心模型

把实际任务能力理解为一个系统问题：

```text
任务结果 ≈ 模型能力 × 上下文有效性 × 环境可执行性 × 验证可靠性
```

Harness 至少包含四部分：

- **Context**：项目结构、需求、设计资料、已有决定和当前状态。
- **Constraints**：范围、技术边界、权限、数据边界、非目标和人工确认门。
- **Tools**：文件操作、终端、测试、构建、浏览器、截图、日志和确定性脚本。
- **Feedback**：报错、测试结果、运行状态、视觉差异、验收记录和回归结果。

不要把 Harness 等同于更长的 Prompt。Prompt 是一次输入；Harness 是让 Agent 能反复读取、行动、观察和修正的工程系统。

## 工作流程

### 1. 先把真实需求变成验收目标

在修改代码前，明确：

1. 谁在什么场景下使用？
2. 输入是什么？哪些字段必填？
3. 输出是什么？用户如何继续使用结果？
4. 核心流程和状态是什么？
5. 明确不做什么？哪些动作不能自动执行？
6. 用什么可观察条件判断完成？

优先选择高频、低风险、输入输出相对稳定的最小任务。不要因为用户说“做个工具”就自行扩展账号、后端、联机、支付或自动外发等范围。

### 2. 建立任务卡

把大任务拆成可独立推进的小任务。每张任务卡写清：目标、涉及文件、完成标准、验证命令、预期副作用和未决问题。

一次优先处理一个相对独立的能力，例如“实现输入表单并通过空输入测试”，不要同时重写 UI、数据模型和部署配置。

交付每张任务卡时，报告：改动文件、行为变化、执行过的验证、失败或未验证部分。

### 3. 编译项目上下文

先读取与当前任务相关的最小上下文：README、项目规则、目录结构、相关源码、测试、设计规范和最近验证记录。

把稳定信息写回项目，而不是只留在聊天历史中：

- README：如何运行、如何操作、如何验证。
- 项目规则文件：命名、目录职责、允许修改的区域和禁止动作。
- docs/design：产品目标、非目标、视觉或交互约定、关键取舍。
- tests：行为契约与边界样例。
- verification：实际设备、浏览器、构建和交付核对结果。

按需读取低频资料。正文保持短而可路由，长规则、模板和历史资料放在有明确用途的引用文件中。

### 4. 先定义约束和确认门

在执行外部副作用前，检查：

- 是否会发送消息、修改线上数据、发布、删除或覆盖文件？
- 是否涉及密钥、个人信息、客户资料或生产环境？
- 当前任务是否真的需要该权限？
- 是否有可逆的草稿或沙箱路径？

默认把外部写入、正式发布、不可逆操作和敏感决策停在人工确认门之前。可以自动生成草稿和测试结果，但不要把“能做”推断成“已获授权”。

### 5. 让反馈回路可执行

采用短循环：

```text
读取事实 → 做一个最小改动 → 运行验证 → 观察反馈 → 定位原因 → 修复并回归
```

优先使用能够给出明确失败位置和下一步线索的检查。把“页面不对”改写为具体现象，例如“手机宽度 390px 时出现横向溢出”或“暂停状态下分数仍然增长”。

不要连续重试直到出现看起来正确的结果。每次失败都要区分：需求不清、上下文缺失、代码错误、环境问题、测试错误或验证范围不足。

### 6. 分层验证

按任务选择最小但足够的验证组合：

- 静态检查：类型、Lint、格式和依赖。
- 单元测试：规则、数据转换、边界和状态变化。
- 集成测试：模块之间的输入输出和错误处理。
- 浏览器或设备检查：真实点击、键盘、触控、布局和状态反馈。
- 构建检查：生产构建和资源打包。
- 人工验收：事实准确、体验可理解、权限和业务边界符合要求。

代码无报错不等于工具可用；测试通过也不等于产品体验和安全边界已经验证。

### 7. 收口与交付

交付前回答四个问题：

1. 另一个人能否按文档复现？
2. 关键用户路径是否有验证证据？
3. 改坏后能否比较和回滚？
4. 下一个人或 Agent 能否继续修改？

记录基线、改动、验证命令、已知风险和未验证部分。把临时对话中的有效规则沉淀到文档、测试或项目规则中；不要把未经验证的推测写成项目事实。

## 常见判断

- Tool 是可调用能力；Skill 是可复用的方法；Memory 是外部持久状态；Harness 是组织上下文、约束、工具、反馈和验证的系统。
- 多 Agent 不是默认更强。只有当任务可以清晰并行、协调成本可控且结果可验证时才拆分。
- Reflection 不是验证本身。模型自评需要外部测试、运行结果、规则或人工反馈支撑。
- 自我修改 Harness 必须有目标、基线、回归集、预算、审批和回滚；不要允许系统无边界地改写自己的规则。
- 真实样例优先于完美样例。为输入缺失、冲突、越界、错误格式和重复执行准备反向测试。
