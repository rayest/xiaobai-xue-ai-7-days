# 讲师演示脚本：从看懂到亲手改一次

按 90 分钟版本准备。以下所有输入框指令均为课堂建议，不是已执行记录。不要在课上临时下载陌生 Skill 或安装一整套依赖。

## 开场 0–5 分钟

讲师说：“你有没有每周都给 AI 重复同一套要求？比如周报要先写结果，会议纪要不能乱补负责人。今天我们把这些方法保存成一个可以反复使用的文件包。”

让学员写下一句重复要求。抽两人回答即可，不讨论平台优劣。

板书三个词：任务、方法、结果。结束时回到这三个词，检查学员有没有拿到自己的方法和结果。

## 演示前：准备环境

建议独立使用复制出来的“实操包”作为课堂项目。这样里面的路径最简单。先打开 `素材/会议记录_标准.md`，把字号放大。让全班看到素材，再看模型输出，避免大家把模型的猜测误当成原始事实。

准备一个尚未发现 meeting-actions 的干净项目用于基线演示。不要在已经装好该 Skill 的同一会话里说“现在不使用 Skill”就当作严格实验；已有上下文会干扰比较。来不及准备时，把比较明确称为“教学对照”，不报告效果倍数。

## 演示一：直接请求整理

聊天输入：

```text
请把素材/会议记录_标准.md 整理为一份会后纪要，输出到练习输出/普通纪要.md。
```

讲师说：“先不评价好不好，我们拿原文检查。”

让学员找三件事：名单负责人是否被编造；9 月 16 日是否成了确定承诺；客服是否被写成已经批准退款。

普通输出如果已处理正确，就承认它做得好。继续说：“我们接下来研究的是如何保存和复用这套要求，不是证明普通对话一定做不好。”

## 演示二：展示 Skill 文件

打开 `skills/meeting-actions/SKILL.md`，只讲四个位置：名称、描述、判断规则、引用格式。再打开 `references/output-format.md`。

讲师说：“前两行帮 Codex 判断什么时候用；正文告诉它怎么判断；格式放在旁边，方便单独维护。这些文件加起来才是我们交付的方法。”

暂时不讲 YAML 的完整语法、Token 预算或工具白名单。学生会看冒号两边是什么即可。

## 演示三：复制并调用

在实操项目里输入：

```text
请把 skills/meeting-actions 整个目录复制到 .agents/skills/meeting-actions。
目标存在时先比较，不覆盖我已有的内容。检查文件完整性后告诉我路径。
```

这是给 Codex 的文件操作请求，不要求学员打开终端。当前官方文档的项目发现位置为 `.agents/skills/`；本机若由插件或历史目录提供同名能力，应确认实际使用的来源。[官方说明](https://learn.chatgpt.com/docs/build-skills)

确保客户端发现后输入：

```text
$meeting-actions 请整理素材/会议记录_标准.md，保存为练习输出/规则纪要.md。
```

检查实际文件读取过程。若发现机制没工作，直接使用按路径读取的备用指令，并说明这一轮没有验证自动发现。

## 演示四：修改一个业务要求

让学员选择“希望任务里多看到什么”，建议选择验收方式。

```text
请修改 .agents/skills/meeting-actions 的输出格式：
给行动项增加“验收方式”一列。仅当原文明确说明时填写；
没有说明则写“待确认”。将对应判断规则写入 SKILL.md。
不要改变已有事实核查规则。
```

注意修改正在被读取的副本，不是留在 `skills/` 的原始样例。若一直使用路线 A，则修改路线 A 指向的样例。讲师让学生看一眼实际修改路径。

重新用标准材料生成新文件。验收方式不应凭空写成“领导签字通过”。“给大家看”可作为原文交付形式，但不应自动变成正式审批标准。

## 演示五：拿困难材料检验

```text
$meeting-actions 整理素材/会议记录_边界.md，保存为练习输出/边界纪要.md。
```

提问：“这个文件没有会议日期，‘明天’能不能自动变成明天的日期？”

正确理解：不知道记录产生日期，就不能用系统当前日期代替。还应保留两个相冲突的交付日期；预算未批准；客户邮件没有授权外发。

如模型犯错，让全班找出缺失的规则或规则未被执行的地方。修改后再测，并检查标准输入没有被破坏。不要为掩盖失败连续重试直到出现好答案。

## 演示六：用自然语言创建新 Skill（120 分钟选做）

当前环境可发现 skill-creator 时输入：

```text
$skill-creator 请在当前练习项目的 .agents/skills 下创建 training-recap。
用途：把培训记录整理为学员复习卡。
输入：课程记录及目标学员，未给学员时说明采用职场初学者假设。
输出：3 个要点、1 个例子、1 道自测题和答案。
规则：材料没讲过的内容标为“补充说明”，不得冒充原课内容。
先做纯文本版本，不加脚本。提供一个测试输入和验收标准。
```

若没有这个工具，去掉 `$skill-creator`，请 Codex 按示例文件结构创建即可。命名不一致时使用实际可用的名称。生成之后，仍然要读文件和测试。

## 课堂失误处理表

| 现象 | 先检查 | 两分钟内的备用 |
| --- | --- | --- |
| `$` 找不到技能 | 打开的项目、实际目录、文件名、重复名称 | 按路径读取 |
| 模型说找不到素材 | 项目根目录、路径前是否需要“实操包/” | 让它列出匹配文件 |
| 修改后没变化 | 是否改错副本、是否仍在旧会话 | 新会话并核对读取路径 |
| 模型没写文件 | 是否有输出路径、写权限是否可用 | 先在聊天中输出再保存 |
| 账号或网络不可用 | 授课账号和模型连接 | 离线分析素材与参考答案 |
| 输出事实有误 | 原文依据、是否触发正确 Skill | 现场定位并重测 |

## 收尾话术

“回去先选一项每周都要做的工作。把两次真实输入和满意结果留下来，写成一个小 Skill，再让同事用新材料测试。先证明这一个有用，再考虑收集更多。”
